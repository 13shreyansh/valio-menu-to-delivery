How a purchasing agent orders from Valio Aimo

This page describes the interface and the operating model: what an agent can see, what it may decide, what goes to a person, and what is still a mock.

Operating model

There is one ordering engine. The portal, Ask Valio and outside agents all call it, so the same request gives the same order and meets the same rules whichever door it comes through.

  1. Read the request. A language model (Gemini) turns words, speech or a photo of a menu into a structured request: dishes and guests, or products and amounts, a day, and any guest diets. It reads Finnish, Swedish and English. It never sets a price, a quantity or a product.
  2. Work out the need. Code multiplies the kitchen's recipes by guests, subtracts stock on hand and what is already ordered for the week, and rounds up to Valio's sales units. A dish with no kitchen recipe gets an assumed recipe, marked for the chef to check.
  3. Look up real offers. Live calls to Valio Aimo's price and availability API for the buyer's customer number: fixed customer price, stock, available date and order-by time. Products are ranked by price per litre or kilogram among those that can deliver the full amount in time: best, better, good.
  4. Apply the buyer's rules. Allergens, limits, swap rules. Anything outside the agent's authority becomes an approval for a named person.
  5. Place or hand over. Within authority the order is placed. Otherwise it waits, with a review link. Price, stock and rules are checked again at the moment of placing.

Tools for agents

The door is a Model Context Protocol server over Streamable HTTP at /mcp/. Every tool publishes a JSON Schema for its input and output and returns typed structuredContent, so any MCP client, or a plain HTTP client speaking JSON-RPC, can use it.

Trust between the agent and Valio

  • Who is calling. Each buyer account has its own bearer token, shown and replaceable in Settings, Connected assistants. No token, no access. The token fixes the customer number; an agent cannot name another customer.
  • What the agent can trust. Every price and stock figure in a result comes from a live Valio API call made for that request, with its time. The portal's "How this was decided" shows each call and its raw response.
  • What the agent cannot do. Approve for a person, change a rule, see another account, or negotiate a price. Text inside a request that tries any of these is ignored.

Exceptions

  • Late or missing stock. The product is ruled out with the reason; the next best offer is proposed, or a recipe-safe swap goes to the chef.
  • Partial availability. The need is filled from the cheapest products first and the split is shown for approval; any shortfall is stated in litres or kilograms.
  • Order-by time passed. The product cannot be ordered for that delivery; the result says when it closed.
  • Edits after approval. An approval covers exact products, quantities and prices. Any change reopens it.
  • Day outside the ordering week. Valio says so and asks for a possible day rather than guessing.
  • Prices move before placing. Everything is re-quoted at placing; if an approval no longer matches, the order goes back for review.

Audit trail

Each order keeps a human-readable record: the request, every Valio call with its time and raw response, the rules applied, who approved what and when, and who placed it. The account log lists orders, approvals, withdrawn approvals, rule changes, token changes and refused agent attempts. Both the buyer and Valio can read the same record.

Assumptions

  • Synthetic data. Catalogue, prices, availability and order-by times are Valio Aimo's Junction 2026 mock, queried live. Nothing here is production data.
  • No order endpoint. Valio's mock has no order API, so a placed order is stored on the account as a demo order and nothing ships. The confirmation says so.
  • Sample kitchen. Hotel Aurora's menu, recipes, bookings, stock and past orders are authored account records. In production they would come from the buyer's menu-planning or stock system.
  • One ordering week. The demo plans week 47 (16 to 22 November 2026) with deliveries on Monday, Wednesday and Friday.
  • Fixed prices. Orders use the customer's fixed price. There is no negotiation or quote step.
  • Assumed recipes. For a dish the kitchen has not recorded, the model proposes a recipe and code maps it to products. It is always marked and always needs a person's OK.
  • Token in place of full OAuth. A per-account bearer token stands in for an OAuth 2.1 client-credentials flow.

Next steps to production

  1. Connect the order step to Valio Aimo's real order API, with idempotency keys and order status callbacks.
  2. Replace the token with OAuth 2.1 and scoped permissions per agent (read, quote, order up to a limit).
  3. Sign price and availability responses (for example JWS over the response body) so a buyer's agent can verify Valio's claims offline.
  4. An approval webhook, so the buyer's own system can route sign-off to the right person.
  5. Read menus, recipes and stock from the buyer's kitchen systems instead of account records.
  6. Use Valio's delivery-reliability and carbon-footprint data in ranking as buyer-set preferences, not only as shown attributes.
  7. Rate limits, anomaly alerts on agent spend, and a Valio-side view of the same audit log.
